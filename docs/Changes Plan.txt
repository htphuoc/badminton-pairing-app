# CẦU LÔNG 360° — REBUILD DATA ARCHITECTURE
# Roles: ADMIN / HOST / MEMBER

We need to upgrade the existing badminton application into a proper database-backed, multi-user, multi-tenant application.

IMPORTANT:

The existing application is a prototype.

DO NOT preserve the existing database structure or existing stored data.

Existing data does NOT need to be migrated.

You are allowed to:

- Redesign the database
- Drop/recreate tables
- Change entity relationships
- Rename fields
- Remove obsolete entities
- Refactor APIs
- Refactor authentication
- Replace localStorage-based persistence
- Change backend architecture where necessary
- Change frontend data access
- Change existing internal models

You only need to preserve the useful existing application functionality and user experience.

DO NOT waste effort building migration logic for existing data.

==================================================
1. CORE OBJECTIVE
==================================================

Transform the current application into:

A secure multi-user
+
database-backed
+
multi-tenant
+
role-based
+
HOST-isolated

badminton management application.

The system must have EXACTLY 3 roles:

1. ADMIN
2. HOST
3. MEMBER

Do NOT create additional roles.

No:

- SUPER_ADMIN
- FULL_ACCESS
- USER_MANAGER
- MANAGER
- STAFF
- MODERATOR

Keep the authorization model simple.

The key authorization concept is:

ROLE + DATA OWNERSHIP

==================================================
2. BUSINESS MODEL
==================================================

The business model is:

ADMIN
    |
    +-------------------------------+
    |               |               |
   HOST A          HOST B          HOST C
    |               |               |
  Group A         Group B         Group C
    |               |               |
 Members A       Members B       Members C
    |               |               |
 Matches A       Matches B       Matches C
 Statistics A   Statistics B   Statistics C
 Settings A     Settings B     Settings C

Each HOST operates an independent badminton group/workspace.

HOSTs must be completely isolated from each other.

==================================================
3. ADMIN
==================================================

ADMIN is the system administrator.

ADMIN has access to the entire system.

ADMIN can:

- Create HOST accounts
- Edit HOST accounts
- Activate/deactivate HOST accounts
- Reset HOST passwords
- View all HOSTs
- View all groups
- View all members
- View all schedules
- View all matches
- View all match history
- View all statistics
- View all group settings
- Manage system settings
- Manage any group
- Manage any member

ADMIN is not restricted by tenant/data ownership.

ADMIN data scope:

ALL DATA

==================================================
4. HOST
==================================================

HOST is the organizer of a badminton group.

A HOST manages:

- Their badminton group
- Their fixed rented court(s)
- Their members
- Their badminton schedule
- Their sessions
- Their pairings
- Their matches
- Their match history
- Their statistics
- Their group settings

A HOST must ONLY access data belonging to their own group.

Example:

HOST A

CAN:
- Group A
- Members A
- Schedule A
- Matches A
- History A
- Statistics A
- Settings A

CANNOT:
- Group B
- Members B
- Schedule B
- Matches B
- History B
- Statistics B
- Settings B

The same applies to every HOST.

==================================================
5. MEMBER
==================================================

MEMBER represents a badminton player/member belonging to a HOST group.

A MEMBER belongs to a specific group.

Initially, MEMBER access should be intentionally limited.

Potential MEMBER capabilities:

- Login
- View own profile
- View own group
- View own schedule
- View own matches
- View own match history
- View limited personal statistics

MEMBER must NOT:

- Manage HOSTs
- Manage other users
- Manage group settings
- Manage members
- Access another HOST's group
- Access another HOST's private data
- Change their role
- Elevate privileges

Build the architecture so more MEMBER functionality can be added later.

Do not overbuild the MEMBER portal in this phase.

==================================================
6. USER ACCOUNT VS BADMINTON MEMBER
==================================================

Separate:

USER ACCOUNT

from:

BADMINTON MEMBER

A badminton member does not necessarily need a login account.

Example:

Member:
- Name
- Gender
- Skill Level
- Member Type
- Phone
- Note
- Avatar

This member may exist only as a badminton participant.

Later, the member can be linked to a login account:

UserAccount
      |
      ↓
Member
      |
      ↓
Group
      |
      ↓
HOST

This allows existing HOSTs to manage members without requiring every member to have an account.

==================================================
7. MULTI-TENANT / DATA ISOLATION
==================================================

Treat every HOST group as an isolated tenant/workspace.

Concept:

TENANT = HOST GROUP

Example:

HOST A → Group A
HOST B → Group B
HOST C → Group C

HOST A must never receive HOST B's data from the backend.

This is a security requirement.

NOT merely a UI requirement.

==================================================
8. BACKEND AUTHORIZATION
==================================================

Authorization MUST be enforced on the server/backend.

Never rely only on:

- React route guards
- hidden menus
- hidden buttons
- localStorage
- frontend filtering
- client-side role checks

Every protected API must determine:

1. Authenticated user
2. Role
3. Group ownership
4. Resource ownership
5. Permission

Example:

HOST A requests:

GET /api/groups/{GROUP_B_ID}/members

Backend checks:

CurrentUser = HOST A

Group B owner = HOST B

Therefore:

DENY

Return:

403 Forbidden

Do not return the data.

==================================================
9. IDOR PROTECTION
==================================================

Protect all APIs from insecure direct object references.

The following must NOT be sufficient to access a resource:

- memberId
- groupId
- matchId
- scheduleId
- statisticsId
- settingsId

The backend must always verify that the requested resource is within the authenticated user's scope.

Examples:

HOST A cannot:

GET /api/members/member-of-host-b

HOST A cannot:

GET /api/matches/match-of-host-b

HOST A cannot:

GET /api/statistics/group-b

HOST A cannot:

PUT /api/groups/group-b/settings

All must be rejected.

==================================================
10. DATA OWNERSHIP
==================================================

Use explicit ownership relationships.

Recommended:

User
  |
  +-- ADMIN
  |
  +-- HOST
       |
       +-- Group
            |
            +-- Member
            +-- Court
            +-- Schedule
            +-- Match
            +-- MatchPlayer
            +-- MatchHistory
            +-- Statistics
            +-- GroupSettings

MEMBER:

User
  |
  +-- MEMBER
       |
       +-- Member
            |
            +-- Group

Do not unnecessarily store HOST_ID in every table if ownership can safely be derived through Group.

However, denormalization is acceptable if there is a clear performance/security reason.

Prioritize:

- correctness
- maintainability
- security
- simple queries

==================================================
19. AUTHENTICATION
==================================================

Implement secure authentication.

ADMIN and HOST accounts require secure credentials.

MEMBER accounts can be created when needed.

Passwords:

- Never store plaintext.
- Use Argon2id or bcrypt.
- Never store passwords in localStorage.
- Never expose password hashes to frontend APIs.

Inactive accounts cannot log in.

Authentication must be server-side.

==================================================

==================================================

Create an initial ADMIN account.

Use secure environment/configuration for initialization.

There should be one initial ADMIN.

ADMIN can subsequently manage HOST accounts.
